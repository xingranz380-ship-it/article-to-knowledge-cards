# HTTP 缓存机制详解

HTTP 缓存是 Web 性能优化中最重要的手段之一。通过合理使用缓存，可以显著减少网络请求、降低服务器负载并提升页面加载速度。

## 缓存的基本原理

当浏览器首次请求一个资源时，服务器会返回资源内容和一组响应头，其中包含缓存指令。浏览器将资源存储在本地缓存中。后续请求相同资源时，浏览器可以直接使用本地副本，而无需重新下载。

缓存的核心价值在于：避免重复传输相同的数据。据统计，一个典型网页中约 60%~80% 的资源是可缓存的静态资源（如图片、CSS、JavaScript 文件）。

## 强缓存与协商缓存

HTTP 缓存分为两种类型：强缓存和协商缓存。

**强缓存**：浏览器直接使用本地缓存，不向服务器发送任何请求。通过 `Cache-Control: max-age=3600` 或 `Expires` 响应头控制。在 max-age 指定的秒数内，浏览器不会发起请求。

**协商缓存**：浏览器向服务器发送请求，服务器根据资源标识判断是否可以使用缓存。如果资源未修改，服务器返回 304 Not Modified，浏览器使用本地缓存；如果已修改，返回 200 和新内容。

协商缓存通过两组头实现：`Last-Modified` / `If-Modified-Since`（基于时间）和 `ETag` / `If-None-Match`（基于内容哈希）。ETag 比 Last-Modified 更精确，因为它能检测到内容变化但修改时间未变的情况。

## Cache-Control 指令

`Cache-Control` 是 HTTP/1.1 中控制缓存行为的主要头，支持多个指令组合使用：

- `public`：响应可被任何缓存（包括代理服务器）存储
- `private`：响应只能被终端用户的浏览器缓存，不能被代理缓存
- `no-cache`：使用缓存前必须与服务器确认（即走协商缓存）
- `no-store`：完全不缓存，每次都必须从服务器获取完整内容
- `max-age=N`：资源在 N 秒内有效，属于强缓存
- `must-revalidate`：资源过期后必须重新验证，不能使用过期缓存

一个常见的配置是：对 HTML 文件使用 `no-cache`（确保每次都检查更新），对静态资源（CSS/JS/图片）使用 `max-age=31536000, immutable`（缓存一年且不可变，通过文件名哈希实现版本更新）。

## 缓存的常见问题

**缓存失效策略**：当资源更新时，如何让浏览器获取新版本？最佳实践是为静态资源文件名添加内容哈希（如 `app.abc123.js`），内容变化时文件名也变化，从而自然绕过缓存。HTML 文件则不设长缓存，确保用户总能拿到最新的资源引用。

**多级缓存**：在浏览器和源服务器之间可能存在 CDN 缓存、代理缓存等多级缓存。`Cache-Control: public` 允许中间缓存存储响应，`s-maxage` 指令专门控制共享缓存（如 CDN）的有效期。

**no-cache 与 no-store 的区别**：很多人混淆这两个指令。`no-cache` 并不是"不缓存"，而是"使用前必须验证"；`no-store` 才是真正的"不存储任何缓存副本"。

## 总结

合理的缓存策略需要区分资源类型：不可变的静态资源设长缓存，动态内容设短缓存或 no-cache，敏感内容用 no-store。理解强缓存与协商缓存的区别、掌握 Cache-Control 各指令的含义，是设计高效缓存策略的基础。
